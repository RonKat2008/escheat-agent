## Findings

### P0

#### R9-01 · The filing agent stalls for minutes and then fails when the server gets other requests during the run
- **Page:** `/close-out/TX` and `/close-out/CA` → "Submit on the replica portal", and `POST /api/agents/file`.
- **Steps:**
  1. Approve the TX report in the runner (typed name, approve anyway).
  2. Click **Run filing agent** and stay on the runner page.
- **Expected:** The receipt in a few seconds. The scripted agent needs about 4 s end to end.
- **Actual:** four attempts.

  | Attempt | Other traffic during the run | Result |
  |---|---|---|
  | TX from the runner (core loop) | Runner page open, waiting for the receipt | Stuck on the "Selected NAUPA file" step for **9 min 24 s**. Then it failed: `locator.innerText: Timeout 30000ms exceeded … waiting for getByTestId('summary-item-count')`. The run lists Duration 9m 25s. |
  | TX retry ("Run filing agent again") | Runner page open | Succeeded after **120 s**. The browser launched at +1 min 56 s, and the rest took 3 s. |
  | CA from the runner | Runner page plus `GET /api/close-out/runner` every 5 s | Failed after about **12 min**: `locator.click … waiting for getByTestId('file-report-link')`. The first runner GET took about 738 s to return. |
  | CA via `POST /api/agents/file` | None for 150 s | **Succeeded in 4 s** (REPL-CA-2026-7RA4RS). |

  - The replica's own screenshot shows the review page rendered correctly (`co9-11c-failed-run-shot5.png`). The agent timed out waiting for a server that was busy elsewhere, not on a broken page.
  - The approval gate held throughout: nothing was submitted without the approval, and "Your approval still covers this file; you can run the agent again" is honest.
- **Cause (hypothesis):** the agent's browser, the replica pages and the app share one `next start` process and one PGlite database. Requests that arrive during a run (the runner page's own refresh, `GET /api/close-out/runner`) appear to queue behind, or deadlock with, the agent's database work. The replica's upload POST then waits minutes. The 1 min 56 s before the retry's browser launch suggests the failed run's resources were still held.
- **Screenshots:** `co9-11b-failed-run.png`, `co9-11c-failed-run-shot4.png`, `co9-11c-failed-run-shot5.png`, `co9-12-TX-receipt.png` (after the retry), `co9-20-CA-failed.png`
- **Suggested fix:**
  - Reproduce with `ESCHEAT_OFFLINE=1` on a production build: start a filing and poll `GET /api/close-out/runner` every 2 s.
  - Look for a PGlite transaction or lock held across a `page.*` await in `executeFiling`, `RunRecorder.step` or `withApproval`. Check that the runner GET does not run `migrate()` or a write on each poll.
  - Give `waitForURL`, `readSummary` and `click` explicit timeouts, and fail the run in under 60 s with a clear message.
  - Add an e2e test that files TX from the runner with the page open, under 30 s.
- **Files:** `src/lib/browser-agents/filing.ts`, `src/lib/browser-agents/run-recorder*`, `src/app/api/close-out/runner/route.ts`, the runner's polling in `src/app/(app)/close-out/`, `src/db/client.ts`

### P1

#### R9-02 · Activity's clock-detection rows are inferred: quick jumps merge onto the wrong day, and moving back erases them
- **Page:** `/activity` after clock moves.
- **Steps:**
  1. Fresh state at Nov 1. Click **+30d** in the clock popover (4 items detected, $3,438.94).
  2. Within the same minute, advance 15 more days (2 items, $288.24).
  3. Open Activity. Then move the clock back 45 days and open Activity again.
- **Expected:** Dec 1 shows "Detected 4 newly stale items · $3,438.94", and Dec 16 shows "Detected 2 · $288.24". Moving back adds a row such as "Removed 6 clock detections". Nothing already recorded disappears.
- **Actual:**
  - Dec 16 shows one row, "Detected 6 newly stale items · $3,727.18 added to the liability", and Dec 1 shows only "Demo clock moved forward".
  - After moving back, the detection row is gone and nothing records the removal (`n9-3-activity-after-back.png`).
  - The page header says "Every entry is a stored row; nothing is inferred."
- **Cause:** `src/lib/queries/activity.ts` builds the row by grouping `stale_items` with `detectedBy = 'clock'` by `date_trunc('minute', created_at)`. It is not a stored event, so it merges any moves made in the same real minute and vanishes when `pruneFutureDetections` deletes the items.
- **Screenshots:** `n9-2-activity-1440.png`, `n9-3-activity-after-back.png`
- **Suggested fix:** write a `clock.detected` activity row in `moveDemoClock` with the count, cents and state breakdown from `ClockMoveResult.detected`, and a `clock.undetected` row when items are pruned.
- **Files:** `src/lib/pipeline/clock-move.ts`, `src/lib/queries/activity.ts`
